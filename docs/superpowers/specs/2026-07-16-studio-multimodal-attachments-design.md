# Studio 多模态附件设计说明

## 目标

为 Studio 主会话增加图片和 DOCX 附件。支持图片的聊天模型直接接收原始图片；纯文本聊天模型通过独立识图模型把图片转述成隐藏文本后继续对话。DOCX 始终在本地解析。附件在用户界面和历史消息中保持原始形态，模型使用的转述或解析文本不混入用户可见正文。同时为模型回复增加“复制为 Markdown”操作。

## 一期范围

- 图片格式：PNG、JPEG、WebP、GIF。
- 文档格式：DOCX。
- 不支持 PDF、PPTX、XLSX、CSV 及其他压缩包或可执行文件。
- DOCX 解析只新增 `python-docx` 依赖。
- 单条用户消息允许同时附带文字、图片和 DOCX；文字可为空，但至少需要一个附件。
- 不增加附件云存储、第三方文件上传或 OCR。

## 模型能力与路由

OpenAI-compatible 的模型列表不提供统一、可靠的多模态能力字段，因此模型能力由用户在模型工作台显式维护。

新增模型能力记录，以 `user_id + provider_id + model` 为唯一键，第一期只包含 `supports_vision`。模型工作台“已连接节点”的每个模型提供“视觉”开关，默认关闭。刷新模型列表不会覆盖已有能力标记；删除提供商时同步删除该提供商的能力记录。

后台模型路由新增 `vision`：

- 当前聊天模型被标记为支持视觉时，图片作为 OpenAI Chat Completions 多模态 `image_url` 内容块直接发送给当前模型。
- 当前聊天模型未标记为支持视觉时，使用 `vision` 路由对应的提供商与模型生成图片转述，再把转述作为隐藏上下文交给聊天模型。
- 未配置 `vision` 路由且当前聊天模型不支持视觉时，本轮在调用主模型前失败，并提示用户配置识图模型。
- 识图调用温度固定为 `1.0`，遵循项目其他后台生成模型的统一温度策略。

能力绑定到具体提供商和模型名称。切换聊天模型后，下一轮自动采用新模型的视觉能力记录，不需要会话级开关。

## 统一资产存储

文件本体保存在：

```text
AgentBI/data/chat-attachments/<user-hash>/<attachment-id>.<extension>
```

SQLite 新增 `studio_assets` 文件对象表，同时索引用户上传附件和对话生成图片，保存：

- 资产 ID 和用户 ID。
- 来源类型：`uploaded` 或 `generated`。
- 资产类型：`image` 或 `docx`。
- 原始文件名、MIME、文件大小和相对存储路径。
- DOCX 提取文本或图片识别转述。
- 生成模型、生成提示词等来源元数据。
- 解析状态、错误信息、创建时间和删除时间。

另增 `chat_message_assets` 关联表，保存消息 ID、资产 ID 和显示顺序。文件对象与消息关系分离，使分支消息可以复用同一份文件和解析缓存，也使对话生图结果能够关联到对应助手消息。

文件上传后先形成用户级临时资产；发送消息时在同一业务流程中绑定到用户消息。服务端校验资产归属，其他用户不能引用资产 ID。对话生图完成后登记生成资产，并在保存卡片事件时关联当前助手消息。创建会话分支时复制消息关联并复用同一资产文件。未绑定消息的临时上传超过 24 小时后可在服务启动或下次上传时清理。

资产通过受控读取接口访问，不直接暴露真实磁盘路径。SQLite 不保存 Base64、图片二进制或 DOCX 二进制。

用户从附件库主动删除资产时采用“软墓碑 + 文件硬删除”：立即删除磁盘文件，将存储路径、DOCX 提取文本、图片识别转述、解析错误和可复用缓存清空，并写入 `deleted_at`。资产 ID、类型、原始文件名和消息关联保留，供历史会话显示“附件已删除”占位。已删除资产不会再进入模型上下文、附件库正常列表或搜索结果。

## 解析与上下文构建

DOCX 上传完成后立即解析段落和表格文本，保留文档内自然顺序和基础分隔。空文档、损坏文档或加密文档返回明确错误，不创建可发送附件。提取文本最多保留 100,000 个字符，超出部分截断并在隐藏文本中标记。

图片不在上传阶段强制调用识图模型：

- 多模态聊天模型直接接收上下文窗口内用户消息的原始图片。
- 纯文本聊天模型在构建上下文时检查图片转述缓存；缺失时通过 `vision` 路由生成并保存，之后复用缓存。
- 同一轮包含多张未识别图片时合并为一次多图识别请求，并按附件名称返回分别对应的描述。
- 用户后续从多模态模型切换为纯文本模型时，历史上下文窗口内尚未转述的图片会按需补充识别，保证上下文连续。

隐藏上下文使用独立的内部消息结构，不改写用户原始 `content`。DOCX 解析文本和图片转述只在对应用户消息进入当前上下文窗口时注入，因此仍服从滚动窗口或压缩上下文策略。

## API 与聊天流程

新增附件上传、资产读取、资产列表、资产统计和删除接口。上传使用 `multipart/form-data`；聊天流接口继续使用 JSON/SSE，只额外接收 `attachment_ids`，避免把 Base64 塞进 `/chat/stream` 请求体。

发送顺序：

1. 前端上传并获得附件 ID。
2. 用户发送消息，前端提交文字和附件 ID。
3. 后端创建用户消息并绑定附件。
4. 上下文服务按当前聊天模型能力构建多模态块或隐藏文本。
5. 主模型照常流式回复；附件预处理状态通过正常错误提示返回，不暴露隐藏转述。

编辑用户消息并重试时保留原附件；第一期不在编辑状态中新增或删除附件。创建分支和切换消息版本时附件随所属用户消息显示。

## Studio 用户界面

输入框增加附件按钮和隐藏文件选择器。选择后在输入框上方显示待发送附件条：

- 图片显示缩略图、文件名、大小和移除按钮。
- DOCX 显示文档图标、文件名、大小和移除按钮。
- 上传、解析和失败状态即时显示；仍在上传的附件不能发送。

消息发送后，附件显示在用户消息正文上方或下方：图片使用受约束的缩略图网格，可点击查看原图；DOCX 使用紧凑文件卡，可下载原文件。模型生成的隐藏图片转述和 DOCX 文本不显示，也不参与“复制用户消息”。刷新或打开历史会话后附件仍可加载。

## 附件库

新增 Studio 独立页面 `/attachments`，从 Studio 导航进入。页面汇总当前用户所有未删除的对话资产：

- 对话生成图片。
- 用户上传图片。
- 用户上传 DOCX。

页面提供“全部、生成图片、上传图片、DOCX”筛选，支持按原始文件名、生成提示词和来源会话标题搜索。图片使用自适应网格，DOCX 使用列表卡；每项显示创建时间、文件大小、来源会话和生成模型或原始文件名。

资产操作包括预览、下载、跳转来源会话和删除。删除前进行二次确认；成功后立即从附件库移除，并按统一删除规则清理文件、DOCX 提取文本和图片转述。若资产仍被历史消息引用，对应消息保留“附件已删除”占位。附件库不提供重命名、标签、批量删除和跨用户共享。

## 复制为 Markdown

模型回复的操作区在“重试”“分支”等现有按钮旁增加“复制 MD”。点击后把该助手消息的原始 Markdown `content` 写入剪贴板，不复制渲染后的 HTML、推理摘要、工具调用详情或结构化卡片。成功后按钮短暂显示“已复制”；剪贴板不可用时显示可恢复的错误提示。

复制操作只针对已完成的助手消息；流式生成期间不显示或禁用。

## 错误处理与限制

- 后端同时校验扩展名、MIME 和文件签名/容器有效性，不能只相信前端 `accept`。
- 文件名在展示时保留，磁盘路径只使用随机资产 ID，防止路径穿越。
- 图片单文件最大 10 MB，DOCX 单文件最大 20 MB；单条消息最多 8 个附件、总大小最大 30 MB。
- 图片直传上游使用内存中的 Data URL，不要求供应商访问本机 URL；不把 Data URL 写入消息表、日志或时间线。
- 识图响应只保存最终转述，不保存模型推理内容。
- 附件上传失败不创建聊天消息；识图失败则终止本轮主模型调用并保留用户消息与附件，允许用户重试。
- DOCX 中的图片、图表、页眉页脚和复杂排版第一期不解析，只提取正文段落与表格文字。
- 删除资产时同步清除图片转述和 DOCX 提取文本；后续上下文构建不得读取墓碑资产。

## 测试与验收

1. 模型能力按用户、提供商和模型独立保存，刷新后仍生效。
2. 模型工作台可配置 `vision` 路由，并显示每个模型的视觉标记。
3. 图片和 DOCX 可上传、移除、随消息发送并在历史会话中重新展示。
4. 标记为视觉模型时，当前模型收到原始图片多模态内容块，不调用识图路由。
5. 纯文本模型只收到隐藏图片转述，转述缓存后不会重复调用识图模型。
6. DOCX 本地提取结果进入上下文但不出现在用户可见消息正文。
7. 没有可用识图路由时给出明确提示，不静默忽略附件。
8. 会话分支、重试和上下文窗口继续正确工作，附件不会因版本切换丢失。
9. 图片缩略图和 DOCX 卡片不会撑破聊天布局。
10. 助手消息“复制 MD”复制原始 Markdown，不包含推理、工具事件和 HTML。
11. 非法类型、超限、损坏 DOCX 和跨用户附件引用均被拒绝。
12. 附件库可以筛选、搜索、预览、下载并跳转到资产来源会话。
13. 删除资产会同步删除磁盘文件、图片转述和 DOCX 提取文本，历史消息显示删除占位。
